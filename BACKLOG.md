## 🔥 Спринт (текущая неделя)

- [ ] **Мелочи** - `RagDocumentMapper`: warning → debug (известное поведение).

- [ ] **SnackBar поверх Drawer**
      При показе SnackBar, когда открыт `ChatHistoryDrawer`,
      сообщение рисуется **ПОД** drawer'ом — пользователь его
      не видит.

- [ ] **Retry для неотвеченных сообщений (user-side)**
      **Сценарий:** пользователь нажал «Отправить», сеть отвалилась
      ДО того, как запрос дошёл до сервера. Сервер **не знает**
      о запросе (никакого failed-сообщения в БД нет). Клиент
      ловит `ClientException` → SnackBar + **удаляет** пустой AI-пузырь.

      **Проблема:** пользователь видит только SnackBar (который
      исчезает). Если он закроет — **не поймёт**, что сообщение
      не ушло. А через несколько минут сервер **может** ответить
      (если запрос всё-таки дошёл) — ответ «внезапно появится»
      при `loadChat`.

      **Что нужно:**
      - `Message.deliveryStatus` (`sent`/`pending`/`failed`) для
        **user**-сообщений;
      - визуальная пометка в `MessageBubble` для **user**
        («Не отправлено» + иконка);
      - кнопка «Повторить» → переотправка.

      **Отличие от retry failed-assistant:** здесь **failed-user** —
      сообщение, которое **не дошло**. Там — сообщение, которое
      **дошло**, но сгенерировать ответ **не удалось**.

      **Дополнительно:** рассмотреть **polling** — если SSE
      оборвался, но сервер работает — периодически проверять,
      появился ли ответ (по `messages` или `previous_response_id`).

- [ ] **Догрузка sources при `loadChat` для `agentic_rag`**
      Подтверждено на стенде: `GET .../messages` не возвращает
      `sources` для RAG (только для `document_chat`). При открытии
      старого RAG-чата из истории sources не отображаются.
      Нужно: после `_setMessages` параллельно вызвать
      `getSources` для каждого assistant-сообщения.
      Срочно — до показа (п. 1.2 из плана).

- [ ] **Закрывать TCP-сокет при watchdog-timeout в SSE**
      Сейчас `AppHttpClient.postStream` при timeout **не** закрывает
      TCP-сокет. Сервер **не** видит обрыва → `is_disconnected`
      не срабатывает → сервер **досчитывает** ответ, который
      «внезапно» появляется при `loadChat`.

      **Ждём ответ от бекендера:** как правильно закрывать
      соединение, чтобы `is_disconnected()` сработал.
      Возможные варианты:
      - отдельный `http.Client` для каждого стрима + `.close()`
        при ошибке/timeout;
      - `request.abort()` (если `http` версия поддерживает);
      - periodic check `is_disconnected()` на сервере
        (если это их зона).

- [ ] **Пометка «Ответ может быть неполным» (partial stream)**
      Если SSE-стрим падает **после** получения **части** текста
      (Wi-Fi моргнул на середине ответа), пользователь видит
      **обрезанный** ответ, но **не понимает**, что он неполный.
      Пример: инструкция «как починить пылесос» обрывается на
      шаге «3. Открутите…» — а что делать дальше, непонятно.

      **Что нужно:**
      - новый статус `MessageStatus.incomplete` (в дополнение к
        `ok`/`failed`/`pending`);
      - `ChatNotifier._markLastAiMessageAsIncomplete(...)` — ставить
        при падении стрима, если `text.isNotEmpty`;
      - `MessageBubble` — плашка «Ответ может быть неполным» под
        текстом;
      - кнопка «Продолжить» (отправить «Продолжи» новым ходом)
        **или** «Повторить» (переотправить исходный вопрос).

      **Зависимость:** сервер **сейчас** не присылает
      `status: incomplete` в `GET .../messages` — надо будет
      согласовать с бекендером. **Пока** — не делаем, ждём
      серверного признака.

      **Приоритет:** высокий для UX, но **не** блокирует показ.

      **Технические грабли (учесть заранее):**
      1. **Стрим + markdown = лаги.** Рендерить markdown на каждой
         дельте дорого (2000 символов × 200 токенов = 200 полных
         перепарсиваний). Решение: во время стрима — `Text`,

         как надо. Решение: свой `MarkdownElementBuilder` **или**
         предобработка (`[1]` → `[1](source://1)` + перехват
         схемы `source://`). Связано с беклогом «Подсветка `[N]`».

      **Пакет:** `flutter_markdown` (актуален) или его форк
      `gpt_markdown` (лучше стриминг, ChatGPT-стиль).

      **Тесты:** golden-тесты на рендер (у нас их сейчас нет —
      придётся вводить).

- [ ] **Разделить `ChatNotifier` на доменные сервисы (SRP)**
      Сейчас ~700 строк, 6 публичных + 13 приватных методов,

      (отправка, retry, загрузка, жизненный цикл, sources).

      state между ними = новый класс багов.

      **Правильно:** вынести логику в **сервисы** без состояния:
      - `ChatMessageSender` — отправка + обработка стрима;
      - `ChatHistoryLoader` — загрузка истории;
      - `ChatSourcesFetcher` — догрузка sources.

      `ChatNotifier` — тонкий: только state + делегирование.

      **Оценка:** 1-2 дня. **Требует:** тесты на `ChatNotifier`
      до рефакторинга (иначе — гарантированные регрессии).
      **Когда:** после показа начальству, но **до** добавления
      фидбека/кеширования/кнопок агентов.

- [ ] **Тесты на `ChatNotifier`**
