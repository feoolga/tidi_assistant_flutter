# Backlog

## Технический долг

### Высокий приоритет

- [ ] **Retry для неотвеченных сообщений (UX-критично)**
      Пользователь отправил сообщение, сеть упала, `SnackBar` показался
      и исчез — но сообщение **осталось** в истории как «отправленное»,
      без ответа. Марья Ивановна не поймёт, что произошло.
      Требует: - `Message.deliveryStatus` (`sent` / `pending` / `failed`); - визуальный индикатор в `MessageBubble` («не отправлено»); - кнопка «повторить» → `ChatNotifier.retryMessage(messageId)`.
      Контекст: обнаружено на скриншоте после Шага 5 (ref.listen).

- [ ] **`event: error` в SSE-стриме — протестировать и покрыть тестом**
      `SendMessageUseCase._parseErrorEvent` **уже** обрабатывает
      `event: error` (README Responses API: `sequence_number: 9999`).
      Но: **нет** теста на реальном потоке, **нет** проверки, что
      `ChatStreamHandler.onError` корректно эмитит `ChatStreamFailed`.
      Требует: интеграционного теста + проверки на реальном бэкенде.

- [ ] **`MessageDto.sources` — УЖЕ ПОЧИНЕНО**
      ~~Было `List<Map>`, стало `List<String>`~~ — сделано в коде.
      **Удалить из Backlog.**

- [ ] **Индикатор частичных ошибок в `ChatHistoryDrawer`**
      После рефакторинга `ChatListNotifier` → `chatsProvider`
      (см. Шаг 4-Refactor): сейчас если **один** агент упал, весь
      список уходит в `AsyncError`. Надо: различать «всё упало» и
      «часть упала, часть загрузилась» + баннер «Часть чатов
      не загружена» с кнопкой «Повторить».
      Требует: расширения `chatsProvider` (например, возвращать
      `({List<ChatSession> chats, int errorCount})`).

### Средний приоритет

- [ ] **Индикатор долгой обработки файла**
      MinerU обрабатывает файл 30–120 секунд (README: `MINERU_TIMEOUT_SECONDS=600`).
      Сейчас пользователь видит спиннер на превью файла и не понимает, идёт
      ли ещё обработка или что-то зависло.
      Требует: текст «Обработка документа... Это может занять минуту» + таймер + опционально «Отменить».

- [ ] **`usage` из `response.completed`**
      README document_chat: в `response.completed` приходит `usage`
      (`input_tokens`/`output_tokens`). Сейчас парсим только `id`, `model`,
      `conversation_id`. Можно показывать пользователю или логировать.

- [ ] **Расширить `AppConfig.allowedMimeTypes`**
      README document_chat: «PDF/DOCX/изображение». MinerU умеет
      DOCX/PPTX/XLSX. Уточнить у техдира, что реально включено
      на деплое, и добавить.

- [ ] **`GET /v1/files`, `GET /v1/files/{id}`, `DELETE /v1/files/{id}`**
      В `AttachmentApi` пока только `uploadFile`.
      Нужно для: удаления файла с сервера при `removeAttachment`,
      отображения «моих файлов», отладки.

- [ ] **`content-type` проверка в `postStream`**
      Если сервер вернёт `200` с `application/json` (а не SSE) —
      парсер попытается читать как SSE и выдаст мусор.
      Требует: проверки `response.headers['content-type']` в `AppHttpClient.postStream`.

- [ ] **Таймаут «нет событий N секунд» в `SseParser`**
      Если соединение подвисло, `sendMessage` может висеть вечно.
      Требует: сторожевого таймера на «нет событий X секунд».

- [ ] **«nginx должен возвращать 502/503 при недоступности мастера, а не 401/404 с FastAPI-дефолтом».


### Низкий приоритет / на будущее

- [ ] **Различение 502 от Master Router и от document_chat**
      Master Router: 502 = агент недоступен.
      document_chat: 502 = MinerU упал.
      Сейчас всегда показываем «Не удалось обработать документ».
      Требует: доработки бэкенда (`error.code`) или разбора тела.

- [ ] **Различение 400 от Master Router и от document_chat**
      Master Router: 400 = невалидное тело или `contract_forms` не совпал.
      document_chat: 400 = файл не обработан.
      Сейчас всегда показываем «Файл ещё обрабатывается».
      Требует: доработки бэкенда (`error.code`).

- [ ] **Показывать `serverMessage` в `userMessage` при 400 в `/v1/responses`**
      Если агент не поддерживает Responses — сервер вернёт 400
      с текстом «Агент X не поддерживает форму Responses API».
      Сейчас пользователь видит «Некорректный запрос».
      Требует: разбора `error.message` для конкретных 400.

- [ ] **413 с `actual_bytes`/`max_bytes` — протестировать, когда бэкенд приедет**
      Бекендер сообщил: «к 413 прикрепляется сообщение с пояснением
      о размере». Клиент **готов** к обоим вариантам
      (`_handleTooLarge` в `AttachmentRepository`).
      Ждём от бекендера `actual_bytes`/`max_bytes` в теле —
      тогда покажем точные цифры. Сейчас nginx отсекает файлы
      **до** бэкенда, поэтому неизвестно, придут ли эти поля.

- [ ] **`error.param` от бэкенда → в `technicalDetails`**
      README: `param` заполняется (`messages.0.role`). Полезно для отладки.

- [ ] **Роли `system`/`developer` в `MessageDto`**
      README: сообщения с этими ролями добавляются к промпту как
      дополнительные инструкции. Пока бэкенд их не присылает
      в истории — задел на будущее.

- [ ] **Явное различение «первое сообщение» vs «с историей» в `_buildInput`**
      Сейчас работает **корректно** (у нас всегда есть `conversation_id`
      в форме Responses). Но при появлении «регенерации» или
      «отправки без сохранения» — сломается.
      Требует: явного флага или проверки на `previous_response_id`.

- [ ] **`ref.onDispose` для `httpClientProvider`**
      Сейчас `AppHttpClient` не закрывается при dispose провайдера.
      Не критично (один экземпляр на приложение), но чисто.
